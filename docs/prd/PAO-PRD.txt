  2. Problem and concept
  PAO applies the Uber/Pathao model to home services. Instead of employing technicians, it
  lets independent providers who are already working nearby sign up, get verified and
  receive bookings.

  Reference point. Sheba.xyz offers similar services (electrician, plumber and so on) in
  Bangladesh, but it delivers them through its own employees. That approach limits how far
  it can scale and how many areas it can cover.

  PAO's approach.

       Open supply. Any qualified local provider can enrol through the Provider app.
       Proximity. Customers see providers near their location, not a central dispatch.
       Choice. Customers compare providers by rating and choose one themselves.
       Fixed pricing. PAO defines every service name and price, so there is no haggling and
       every provider charges the same for the same job.
       Trust as the core product. Providers enter people's homes, so verification is
       mandatory. Without it the platform cannot operate (section 6).

  5. Core booking flow and business rules
  In PAO, the customer chooses the provider and the provider accepts or rejects. The
  platform never assigns a job automatically in the MVP.

  Happy path (on-demand job).

   1. The customer opens the app, which detects their location or lets them pick a saved
      address.
   2. The customer taps a service and picks a sub-service and quantity. The fixed price is
       shown.
   3. The app lists verified, online providers within the search radius, sorted by distance and
       rating. Each card shows the provider's name, photo, verification badge, rating, number
       of completed jobs and distance.
   4. The customer opens a provider's profile, chooses a time ("as soon as possible" or a
       scheduled slot) and confirms the booking.
   5. The provider receives a push notification and has a time limit to accept or reject.
   6. If the provider accepts, the customer sees the confirmation and the provider's contact
       details. If the provider rejects or the time runs out, the customer is asked to pick
       another provider.
   7. The provider marks "On the way", then "Arrived". The provider starts the job by
      entering a 4-digit start code that the customer reads from their app.
   8. The provider marks the job complete. Payment is settled (cash in the MVP), and both
       sides rate each other.

  6.3 Level 2 — skill and field verification
  Level 2 adds an in-person check of the provider's actual work on top of their documents.

        PAO schedules an in-person interview or skill test, at a PAO location or a supervised
        real job.
        The verifier records the outcome in the admin panel using a per-service checklist (for
        example, an electrician checklist covers safe wiring, tool use and earthing awareness).
        Optional: a physical address visit, recorded with photos and the GPS position.
        Result: pass, fail or retest. A failed provider stays at Level 1 and may retry after a
        cooling-off period.

  6.4 Ongoing trust
        Re-verification. The police clearance certificate expires every 12 months and NID data
        is re-checked if the profile changes. An expired document suspends bookings
        automatically until it is renewed.
        Quality thresholds. A rating below a set floor (e.g. 3.5 after 10 jobs), repeated
        cancellations or a verified complaint triggers review or suspension.
        Audit trail. Every verification decision stores who decided, when, what was decided
        and why. These records cannot be edited.
        Account status. Pending → Active → Suspended → Banned. Banned identities (NID,
        phone, face) cannot re-register.

  6.6 Handling of verification data
  NID images, selfies and police certificates are sensitive personal data.

       They are stored in private object storage and accessed only through short-lived signed
       URLs.
       They are encrypted at rest and visible only to admin roles with the verification
       permission. Every view is logged.
       They are never returned by any customer-facing API. Customers see only the badge,
       never the documents.
       Retention: documents are kept while the account is active, plus a fixed period after
       closure (to be decided in line with Bangladeshi law).

  9.3 Module boundary rules (what makes the later split easy)
   1. One contract package per module. Each module has a contract/ folder. Its
        service.go file holds the module's service-to-service interface, which is the only set
       of methods other modules may call. The same folder holds the request/response DTOs
       and event definitions (this is the separate service-to-service file you asked for).
   2. Import only contracts. Module A may import moduleB/contract and nothing else
       from module B. This is enforced by a lint rule in CI (e.g. depguard or go-arch-lint).
   3. Own your data. Each module has its own Postgres schema ( booking.* , catalog.*
       and so on). There are no joins or foreign keys across schemas, and one module never
       reads another module's tables.

PAO — Product Requirements Document

   4. Copy, don't reference. A booking stores snapshots (price, service name, provider
       display name) rather than reading them live from other modules.
   5. Events for side effects. Modules publish domain events (e.g. BookingAccepted ) on an
       in-process event bus interface, and other modules subscribe. Events are written
       through an outbox table so the bus can later be swapped for NATS, RabbitMQ or Kafka
       without changing module code.
   6. No cross-module transactions. A transaction never spans two modules. Workflows
      that touch several modules use events or explicit compensation.
   7. Swappable implementations. In the monolith, the contract interface is implemented
      by an in-process adapter. In a microservice, the same interface is implemented by an
       HTTP/gRPC client. Calling code does not change.

  10. Engineering and documentation standards
  The MVP is built by AI but maintained by humans. Every rule below exists so that a new
  engineer can open the repository and be productive within a day.

  Code style: it must read as if a careful human wrote it.

       Names carry the meaning: AcceptBooking , providerID ,
        ErrBookingAlreadyAccepted . No generic data , handleStuff or utils2 .
       Comments explain why, never what. No comment on every line, no banner comments,
       no restating the code, no leftover AI notes such as "Here we…" or "// Step 1".
       Functions are small and do one thing. A deeply nested function is a sign it needs
       splitting.
       Code follows the standard formatters and linters: gofmt , golangci-lint , dart
       format , flutter analyze , with the lint config committed to the repository.
       No dead code, commented-out code, or TODOs without an issue reference.

  Design principles.

       SOLID.
            Single responsibility per type and function.
            Open/closed through interfaces: a new SMS provider is a new adapter, not edits to
            existing code.
            Liskov: every adapter honours its port's contract.
            Interface segregation: small ports.
            Dependency inversion: use cases depend on ports.
       Repository pattern. All database access goes through repository interfaces in port/ .
       SQL lives only in adapter/postgres .
       Clean architecture. The layering and boundary rules in sections 9.3 and 9.4 are
       mandatory, and CI fails the build when they are broken.
       Explicit errors. Errors are wrapped with context and mapped to API error codes at the
       HTTP edge only.

  Testing (a task is not done until its tests pass).
